# 05 動手改程式配方

本手冊為《企業破產預測專案》的進階實作指南，提供 7 個高頻且具實戰價值的「程式修改配方」。每個配方均遵循嚴格的工程規範與方法論邊界，旨在指引學習者在不破壞歷史實驗可重現性與防洩漏機制的前提下，安全地擴充模型、前處理轉換器、評估指標與應用層介面。

---

## 核心安全準則與操作邊界

> [!CAUTION]
> **原始碼絕對保護原則**：
> 1. 本手冊中的所有配方僅為程式碼修改範例與擴充指引，**嚴禁在專案正式目錄中直接修改原始碼或重新解封測試集**。
> 2. 若欲進行新模型或新特徵實驗，請建立專案副本（僅複製 `bankruptcy/src/` 與 `bankruptcy/config.py`，**嚴禁複製** `outputs/`、`splits.joblib`、`E6_LOCK`、`data/`），並在副本上使用合成資料或新切分進行驗證。
> 3. 已固化的 E6 測試集結果具有不可重複的嚴格防護；任何更動模型或特徵空間之修改，均與現有 E6 結果**不可直接比較**。

## 配方 2：新增一個前處理 transformer（以 RatioFeatureAdder 為例）

- 目標：依循專案規範繼承 `BaseEstimator` 與 `TransformerMixin`，實作無洩漏的特徵比率轉換器 `RatioFeatureAdder`，並示範防洩漏單元測試如何偵測錯誤的全域轉換器。
- 前置知識：閱讀 [02_管線架構.md](02_管線架構.md) 與 [03_前處理.md](03_參數手冊/03_前處理.md)。
- 風險等級：【中】改 src 但不影響固化產物（若僅在自建管線中使用）／【高】會使固化產物失效（若插入既有正式管線改變特徵維度）。
- 需要修改的位置：
  - `bankruptcy/src/preprocessing.py:27` (`BaseEstimator`)
  - `bankruptcy/src/preprocessing.py:27` (`TransformerMixin`)
  - `bankruptcy/src/pipelines.py:212-258` (`build_pipeline`)
- 步驟：
  1. **實作防洩漏 Transformer**：在 `bankruptcy/src/preprocessing.py` 中繼承 `BaseEstimator, TransformerMixin`，`fit` 僅校驗維度，`transform` 逐列計算（示意代碼，未在專案中實際修改）：
     ```python
     class RatioFeatureAdder(BaseEstimator, TransformerMixin):
         def __init__(self, col1_idx: int = 0, col2_idx: int = 1, epsilon: float = 1e-6):
             self.col1_idx = col1_idx
             self.col2_idx = col2_idx
             self.epsilon = epsilon

         def fit(self, X, y=None):
             X_arr = np.asarray(X)
             self.n_features_in_ = X_arr.shape[1]
             if self.col1_idx >= self.n_features_in_ or self.col2_idx >= self.n_features_in_:
                 raise ValueError("Column index out of bounds")
             return self

         def transform(self, X):
             X_arr = np.asarray(X)
             if X_arr.shape[1] != self.n_features_in_:
                 raise ValueError("Feature count mismatch")
             col1 = X_arr[:, self.col1_idx]
             col2 = X_arr[:, self.col2_idx]
             ratio = (col1 / (col2 + self.epsilon)).reshape(-1, 1)
             return np.hstack([X_arr, ratio])
     ```
  2. **對比洩漏版錯誤實作**：反面教材 `LeakyMeanScaler` 在 `transform` 中使用整批資料的均值 `np.mean(X_arr, axis=0)`，使得單筆樣本的轉換結果受到同批次其他樣本的污染。
  3. **將 Transformer 插入管線**：在 `bankruptcy/src/pipelines.py:212-258` 的 `build_pipeline` 函式中，將新步驟插入 `steps` 列表（例如置於 `large_value_indicator` 之後或 `scaler` 之前）。
- 必補的單元測試：
  - 測試名稱：`test_ratio_feature_adder_contract` 與 `test_leakage_detection`
  - 驗證內容：
    1. 驗證 `fit` 與 `transform` 分離，對不同筆數（不同批次大小）之輸入均可正確輸出。
    2. **行獨立性測試（Row-Independence / Leakage Detector）**：單一樣本 $A$ 獨立輸入轉換後的數值，必須與樣本 $A$ 混入批次 $[A, B, C]$ 後對應列的數值**完全逐位一致**（`assert_allclose`）。
  - 放置檔案：`tests/test_recipe_2_transformer.py`。
- 防洩漏檢查：
  - `transform` 函式內部嚴禁出現 `np.mean(X)`、`np.std(X)`、`np.quantile(X)` 等跨列聚合運算。所有用於正規化之統計量，必須在 `fit` 期間僅使用訓練折資料計算完畢並儲存為屬性（如 `self.mean_`）。
- 驗證方式：
  - 在沙盒執行洩漏檢測單元測試：
    ```powershell
    python -m unittest scratch/recipes/tests/test_recipes_demo.py
    ```
  - 預期輸出：
    `[Recipe 2 Demo] Clean transformer passed row-independence (no leakage).`
    `[Recipe 2 Demo] Leak detector successfully flagged LeakyMeanScaler! (max discrepancy: 154.6667)`
- 常見的坑：
  - 坑 1：在 `__init__` 中快取資料陣列或執行計算，違反 scikit-learn 規範（`__init__` 僅能接收並綁定超參數）。
  - 坑 2：未考慮分母接近 0 或等於 0 的情況，未加入數值穩定常數 `epsilon`，導致產生 `inf` 或 `NaN`。
- 如何復原：
  - 還原 `bankruptcy/src/preprocessing.py` 與 `bankruptcy/src/pipelines.py`。
- 這個修改會讓哪些固化產物失效或需要重建：
  - 若在正式管線中啟用此步驟，特徵維度將發生改變（如由 72 欄變為 73 欄），導致既有最佳超參數（`best_params/*.json`）、特徵重要度分析（`e5_shap_summary_*.png`）、固化模型權重（`outputs/models/final/*.joblib`）以及 `defaults.json` 全數失效，需自 E1 重新執行全流程。

## 配方 4：新增評估指標（以 precision_at_top_k 為例）

- 目標：新增業務預算導向指標 `precision_at_top_k`，支援悲觀同分處理並納入模型評估報表。
- 前置知識：閱讀 [09_門檻與目標.md](03_參數手冊/09_門檻與目標.md) 與 [04_實驗操作指南.md](04_實驗操作指南.md)。
- 風險等級：【低】只改文件與 lab，或只在評估報表中擴展欄位，不影響特徵或模型。
- 需要修改的位置：
  - `bankruptcy/src/metrics.py:108` (`alert_ratio_at_recall`)
  - `bankruptcy/src/metrics.py:202` (`evaluate_scores`)
  - `bankruptcy/src/metrics.py:342` (`recall_at_top_k_percent`)
- 步驟：
  1. **實作指標計算函式**：在 `bankruptcy/src/metrics.py:342` 旁新增 `precision_at_top_k`，採用專案既有悲觀同分規則（以下程式碼為示範示意，未在專案中實際修改）：
     ```python
     def precision_at_top_k(
         y_true: ArrayLike,
         score: ArrayLike,
         k_percent: float = DEFAULT_TOP_K_PERCENT,
         method: str = "floor",
     ) -> Optional[float]:
         if not (0.0 < k_percent <= 1.0):
             raise ValueError(f"k_percent must be in (0, 1], got {k_percent}")
         y_arr, s_arr, P, N = _validate_inputs(y_true, score)
         k = compute_top_k_quota(N, k_percent=k_percent, method=method)
         if k is None or k <= 0:
             return None
         if k >= N:
             return float(P / N)
         sorted_scores = np.sort(s_arr)[::-1]
         thr = sorted_scores[k - 1]
         strictly_greater = s_arr > thr
         tp_strictly_greater = int((strictly_greater & (y_arr == 1)).sum())
         rem = k - int(strictly_greater.sum())
         tied_mask = s_arr == thr
         tied_negatives = int((tied_mask & (y_arr == 0)).sum())
         tp_from_ties = max(0, rem - tied_negatives)
         total_tp = tp_strictly_greater + tp_from_ties
         return float(total_tp / k)
     ```
  2. **登錄至多指標評估字典**：在 `bankruptcy/src/metrics.py:202` 的 `evaluate_scores` 函式中，加入新指標欄位：
     ```python
     results["precision_at_top_10pct"] = precision_at_top_k(y_true, score, k_percent=0.10)
     ```
- 必補的單元測試：
  - 測試名稱：`test_precision_at_top_k_hand_calculated`
  - 驗證內容：使用 20 筆樣本之玩具資料（包含 2 筆正樣本與同分樣本），以手算推導真值驗證：
    - 正負樣本完全分離時（理想排序）：預算 $k=2$，2 筆正樣本全中，精確率為 $2/2 = 1.0$。

  - 放置檔案：`tests/test_recipe_4_metrics.py`。
- 防洩漏檢查：
  - 評估指標僅作為事後驗證與報告呈現，嚴格不反饋至模型損失函數或特徵權重更新中，不存在資料洩漏問題。

## 配方 6：換成真實世界資料重做（9 大檢查清單 - 最重要）

- 目標：將整套破產預測機器學習系統遷移至真實金融世界資料集，系統性防範 9 大核心陷阱。
- 前置知識：閱讀全體導讀手冊與 [01_資料與切分.md](03_參數手冊/01_資料與切分.md)。
- 風險等級：【高】會使固化產物或 E6 結果不可比（全專案重構）。
- 需要修改的位置：
  - `bankruptcy/src/cv.py:197` (`get_train_data`)
  - `bankruptcy/config.py:23` (`TEST_SIZE`)
  - `bankruptcy/src/scoring.py:32` (`MAX_MISSING_FEATURE_RATIO`)
- 步驟：9 大檢查清單逐項落實：
  1. **欄位對映與標籤口徑**：
     - *為什麼會出問題*：真實財報資料中，「破產」之時間窗口（如破產前 1 年 vs 前 3 年）、法律定義（聲請重整 vs 清算解散）以及會計準則（IFRS vs GAAP）若不一致，將導致標籤混亂與假性關聯。
     - *怎麼驗證*：建立明確的標籤規格文件，對輸入 CSV 進行欄位型別校驗與幣別/單位轉換檢核。
  2. **時間結構與防止跨年度洩漏（本專案之核心限制）**：
     - *為什麼會出問題*：真實資料通常包含「公司統編/代號」與「財報年度」。若將同一家公司不同年度的財報隨機打散至訓練集與驗證集，模型將學會記住特定公司的靜態特徵（如股本大小），導致嚴重的跨時間洩漏（Out-of-Time 崩塌）。
     - *怎麼驗證*：**本專案目前資料因去識別化而無公司 ID 與年份，故採用 StratifiedKFold；若換成真實資料，必須強制改用 `GroupKFold(groups=company_id)` 或依年度切分的滾動時間序切分（Rolling Window Split）**。
  3. **盛行率變化與貝氏調整**：
     - *為什麼會出問題*：本資料集的正樣本率為 3.23%（約 1:30），而真實市場破產率通常更為罕見（如 1.0% 或 0.5%）。
     - *怎麼驗證*：依據 E7a 貝氏調整公式（此處為玩具推演，非專案實測數值）：
       $$Precision = \frac{\text{Recall} \times \pi}{\text{Recall} \times \pi + (1 - \text{Specificity}) \times (1 - \pi)}$$
       當盛行率 $\pi$ 由 3.2% 下降至 0.5% 時，即便維持相同敏感度與特異度，精確率將大幅縮減約 6 倍，預警家數相對實際破產家數的預警倍數（AR）將顯著膨脹。必須在業務端重新校估調查負擔。
  4. **特徵分佈漂移（Covariate Shift）**：
     - *為什麼會出問題*：`QuantileScaler` 與 ECDF 參考分佈是在歷史訓練資料上擬合。若遭遇總體經濟劇變（如升息或通膨），新資料的分佈位移會使分位數映射完全失真。
     - *怎麼驗證*：計算各特徵之母體穩定性指標（PSI, Population Stability Index）或雙樣本 KS 檢定，PSI > 0.25 者應觸發重新擬合警報。
  5. **缺值分佈與容忍度**：
     - *為什麼會出問題*：`scoring.py` 設有 20% 缺失率上限（`MAX_MISSING_FEATURE_RATIO = 0.20`）。真實小型企業可能缺失大量財務比率。
     - *怎麼驗證*：統計各產業缺值分佈，必要時導入多重插補或樹模型原生缺值處理。
  6. **需重建之固化產物清單**：
     - *為什麼會出問題*：舊專案的全部固化產物對新資料均無效。
     - *怎麼驗證*：在新專案倉庫中依序完整重建：`splits.joblib`、`best_params/*.json`、`thresholds.json`、`defaults.json` 以及 `outputs/models/final/*`。
  7. **失效之專案先驗假設**：
     - *為什麼會出問題*：本專案預設的 95 個特徵、3.2% 盛行率、TEST_SIZE=0.2、近重複樣本剔除閾值、E6 固定 44 家正樣本等數值將全數失效。
     - *怎麼驗證*：重新執行 E0a 資料審計，建立新資料集的基準規格報告。
  8. **新測試集規劃與物理鎖定**：
     - *為什麼會出問題*：嚴禁沿用或提前窺探新資料的測試集。
     - *怎麼驗證*：在新專案初期即建立獨立的 Holdout 測試集與 `E6_LOCK` 防護機制，確保推論前全體開發人員與調參腳本對測試集不可見。
  9. **外部驗證嚴正聲明**：
     - **外部驗證尚未做，目前所有結果只代表這一份資料，不能代表真實世界的表現！在未完成跨市場與滾動時間序列驗證前，絕不可直接上線投資決策**。
- 必補的單元測試：
  - 測試名稱：`test_real_world_group_leakage_detector`
  - 驗證內容：驗證同公司不同年度無跨折洩漏。
  - 放置檔案：`tests/test_splits.py`。
- 防洩漏檢查：
  - 嚴格落實 Point-in-Time 資訊邊界，任何特徵工程與標籤建立只能使用財報發布日以前的公開資訊。
- 驗證方式：
  - 執行資料審計腳本並檢查報告：`python bankruptcy/src/data_audit.py`（注意：此指令會覆寫 `outputs/tables/audit_summary.csv` 等產物，【可重跑但會覆寫 outputs，需先備份】；在真實世界資料重做時請於新專案目錄下執行）。
- 常見的坑：
  - 坑 1：忽視存活者偏差（Survivorship bias），僅抓取目前依然上市存續的公司，剔除已破產下市者，導致樣本嚴重失真。
